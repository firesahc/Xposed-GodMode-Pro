# 6.10 IPC 与权威边界

## 目标

6.10 在保留 `RuleRecord` JSON、Parcelable、ZIP V1、图片路径和匹配/执行语义的前提下，收敛跨进程边界。规则数据不迁移、不重新解释；变化只发生在“谁能写、如何通知、如何判断服务是否可信”。

## 唯一 IPC 合同

- system_server 注册 `godmode`，实现 `ipc.contract.IRuleService`。
- 客户端先校验 Binder descriptor，再用 transaction 1 读取 `ServiceIdentityParcel`；
  协议版本、构建版本、合同指纹任一不一致时进入 `REBOOT_REQUIRED`，不回退到旧 AIDL。
- 当前合同指纹为 `iruleservice-61000-fd-mutate-v3`。同为 61000 但仍使用旧图片
  会话的客户端或 system_server 会在握手阶段被拒绝，更新 APK 后必须重启系统。
- Binder 死亡只清理当前 Binder 身份；新连接仍必须重新握手。
- 规则读取使用只读 `SharedMemory` 快照，内容仍是现有 `AppRules`/`ActRules` JSON。
- 规则变更通知只携带包名和 committed generation；编辑通知携带 edit revision。
  客户端按连接 epoch、revision 和 generation 丢弃迟到事件，再读取完整快照。

## 写入权威

system_server 内的 `RuleRepository` 是唯一规则写入入口。所有普通写入、图片保存、
删除和工具栏设置经过同一服务状态检查。编辑是全局许可，不绑定单一目标：编辑开启后，
多个已注入目标进程可以并发申请短 `OP_MUTATION`，但每个调用 UID 只能修改它所拥有的
请求包，且 `RuleRecord.packageName` 必须与请求包一致。这里的“UID 拥有包”兼容 shared UID，
不宣称能识别 shared UID 中的具体进程包。

管理端无需开启编辑即可直接修改任意合法包；工具栏配置使用管理端专属的全局 mutation。
工具栏配置读取使用包作用域：管理端读取 `GLOBAL_SCOPE`，目标进程只能读取其 UID
拥有的包；读取权限不等于配置写入权限，写入仍只允许管理端。
关闭编辑先进入 `CLOSING`，拒绝新的目标 mutation，并最多等待 10 秒让已经进入会话的提交
完成。超时返回 `BUSY` 且继续保持关闭中，客户端保留 token 但禁止重新开启；收到服务端的
关闭 revision 后才清除 token。管理端 owner 死亡也执行同一
关闭流程；正在持久化的提交允许完成。

图片写入不再预先向 system_server 申请资产会话。客户端取得 mutation 租约后，为主图和
修改图各创建一个匿名 pipe，并同时启动两个 `GM-FD-Writer` 写线程；一次 `mutate()` 直接
携带 `RuleRecord` JSON 与两个可空输入 FD。服务端完成权限、包名和租约校验后，才把 pipe
有界复制到包私有目录的 `.incoming-*` 文件，执行现有安全解码，再调用 `RuleRepository`
原子发布。临时文件总在 `finally` 中删除，旧版 `.asset-*` 遗留只在启动清理时识别。

恢复和备份使用管理端独占维护租约，仅能在编辑已关闭且没有未完成 mutation 时开始。
维护期间所有普通 mutation 返回 `BUSY`；恢复失败不会伪造空规则目录。

备份使用独占的 `OP_BACKUP` 读租约。租约期间服务端拒绝所有 mutation，客户端重新读取权威规则快照并通过受限图片 FD 导出，完成或 owner 死亡后释放租约。
恢复按条目返回 `RestoreReport`：单条规则及其图片必须同时成功，损坏、缺失、越界或
无法解码的图片只拒绝当前条目，其他条目仍可继续恢复。归档内图片路径只用于定位输入，
不会作为清空图片路径后继续提交的降级路径；服务端只有在新图片和规则文件都持久化成功后
才发布缓存、generation 和 Observer。

Binder 回复可能在磁盘提交后丢失。普通 mutation 仍通过目标包权威快照对账；启用撤销
捕获的编辑器 mutation 则以原始 requestId 查询服务端幂等结果，并可用
`UndoStateParcel.topSourceRequestId` 确认提交是否进入权威历史，不能因回包丢失重放写入。

## 权威撤销账本

注入编辑器产生的屏蔽和属性修改可请求 `captureUndo`。`RuleRepository` 在规则写入的同一
线性化锁内捕获槽位 before/after、canonical 摘要、图片引用和单调 lineage，并把历史写入
system_server 中容量为 10 的 `AuthoritativeUndoJournal`。CREATE 或 UPDATE 由提交前槽位
是否存在决定，不从 mutation 名称推断。管理页写入、删除、恢复以及其他未捕获操作都会
推进槽位 lineage，使旧历史在内容经历 ABA 后仍不能误撤销。

历史作用域为服务端分配的进程 owner、调用 UID、包名和 edit revision。短 mutation lease
只保护一次提交；历史另行监听进程级 `ILeaseOwner` 死亡。Activity 和编辑面板切换不清理
历史，owner 死亡、编辑关闭、容量淘汰和显式失效会释放历史图片引用。账本不落盘，
system_server 重启后自然为空，规则加载完成后仍执行孤儿图片清理。

system_server 内部由 `OperationLeaseController` 独占短操作租约、Binder death 注册和
`begin/finishPersistence`，并用幂等 permit 保证每次持久化只完成一次；服务关闭会先停止
发放新 permit，并等待全部已发放 permit 完成后再关闭 Repository。历史生命周期由
`EditorHistoryOwnerRegistry` 独立持有：进程级 owner 负责 death，`(owner, editRevision)`
epoch 负责在途访问和延迟清理。编辑关闭时先注销已释放的 edit token，再按
`closedEditRevision` 精确撤销旧 epoch，最后发布 edit-disabled observer；不得按当前
revision 推导旧 revision，也不得执行跨 revision 的全量历史清理。`getUndoState()` 在
Repository 查询前后都校验原子 edit phase/revision 和 history lease 活性，关闭过程中只允许
读取已存在的 epoch，因此关闭或新会话切换期间不会返回旧 revision 的成功状态。以上均为
system_server 内部拆分，不改变 AIDL、Parcelable、v3 指纹或 Repository 权威事务边界。

客户端只持有 `UndoStateParcel` 投影。`undoLatest()` 携带新的 requestId、mutation lease、
预期 edit revision、history revision 和 top sequence，服务端以 CAS 校验后执行权威逆事务。
重复 undo requestId 返回原结果，不会继续弹出下一条历史；旧 UI 状态返回 `STALE`。
连续同槽撤销会在恢复前态后重新绑定下一条历史的预期 lineage，从而支持
`R0 -> R1 -> R2` 依次回到 `R1 -> R0`。撤销成功只发布新 generation，界面恢复继续经过
现有 `Observer -> RuleDiff -> ViewController`，客户端不得先执行本地 revoke。

canonical 规则和所有 journal 引用共同决定图片文件是否可删除。UPDATE 捕获前先 pin before
图片；撤销后 before 重新成为 canonical，after 仅在不再被 canonical 或其他历史引用时删除。
完整状态比较使用 canonical 扁平 JSON，禁止使用只比较槽位的 `RuleRecord.equals()` 或字段
不完整的 `contentEquals()`。

## 旧代码清理

6.10 客户端和服务端均只引用新合同；旧 `IGodModeManager`、`IObserver` AIDL 以及
`AssetWriteSession`、`openAssetWrite()`、`discardAssetWrite()` 已删除。
`RuleServiceClient` 保留为应用侧门面名称，但内部只实现新合同。旧规则文件和
`RuleRecord` 保留，因为它们是数据格式，不是 IPC 兼容层。

## 注入与 Recycler 稳定性

IPC 握手失败时，`AppInjector` 不安装业务 Hook，避免半初始化状态进入宿主进程。Recycler 的 `notifyDataSetChanged`、`bindViewHolder`、`onViewRecycled` 三个 Hook 分开安装：某个 ROM 缺少一个方法时，其他可用 Hook 仍能工作，后续重试也不会重复安装已经成功的 Hook。Hook 回调内部的异常只记录并结束本次处理，不向宿主应用抛出。

这部分只保护安装和生命周期，不改变 `RuleRecord` 的匹配、应用或撤销语义；图片请求仍由现有的请求代次和 View 状态校验防止迟到结果覆盖新绑定。

编辑器交互 Hook 使用独立的运行时 gate：编辑器关闭时，Touch 和 Key 回调立即返回；只有编辑器明确接管事件时才修改宿主返回值。音量键的双击时间使用单调时钟，Hook 异常不会改变宿主默认行为。自动规则核心只依赖生命周期 Hook 和 EventBus，Touch、Key 以及 Recycler 可选 Hook 的安装或回调失败不会改变核心就绪状态。

编辑器面板复用现有 Activity 引用和会话代次保护异步回调。Activity 切换或销毁会使旧会话失效，延迟显示、截图、保存、图片选择和撤销回调在更新界面前重新校验 Activity、DecorView root 和目标 View。保存期间收到关闭请求会延迟到保存成功、失败或中止后的统一清理路径执行。Recycler 的 bind/recycle 快速路径按目标 ClassLoader 隔离，只有两者成对安装时才启用；无 repeatable 规则时仅关闭逻辑 gate，不动态卸载物理 Hook。

布局反馈仍使用基线 `OnGlobalLayoutListener`、首帧 `decorView.post()` 和 50ms 防抖。`mSelfTriggeredLayout` 只在 `ViewController` 确认实际物理写入后设置，匹配失败、异常或无变化不会伪装成自身布局；自身标记最多消费一次，从而不吞掉后续真实布局事件。

## 客户端故障投影

客户端将桥接缺失、服务启动中、Binder 断开、descriptor 或合同不匹配、
权限拒绝和操作占用投影为结构化诊断。UI 只显示简明原因与可执行建议，
底层 Binder 异常仅保留在持久化日志中；只有真实 descriptor/合同不匹配才提示更新并重启。

## 编辑截图投影

创建和修改规则共用编辑器编排层的截图入口。截图必须在主线程执行，
临时隐藏工具栏、属性面板和高亮遮罩，并在 `finally` 中恢复每个覆盖层原始可见状态。
截图失败时不发起规则写入。屏蔽和属性修改只有在权威提交成功后才更新撤销状态；屏蔽
失败使用当前 Activity 的 `ViewController` 恢复乐观隐藏。撤销按钮位于修改菜单之后、上下
导航之前，在空历史、提交中或撤销中禁用。`BUSY`、`WRITE_FAILED`、`UNCERTAIN` 保留当前
投影供对账或重试；`STALE`、`EXPIRED`、`OWNER_MISMATCH` 刷新权威状态并提示失败。

## 验证边界

Java/AIDL 编译和 APK 构建只能证明接口与打包正确，不能证明 LSPosed 注入、真实 system_server Binder、SELinux/owner、ROM 差异或 RecyclerView 快速复用。发布前仍需在目标 ROM 上串行验证这些场景。

当前候选的具体执行结果以本分支最终提交和 CI 记录为准。JVM、构建、lint、静态合同和
API 35 emulator instrumentation 必须分别记录，不能互相代替。真实设备上的 system_server
注册、Binder owner death、LSPosed 注入、SELinux/owner、不同 ROM Hook 点、快速 fling、
detach/destroy 和异步图片回调也必须在同一候选 SHA 上执行，不能由模拟器或旧候选结果替代。
所有设备测试还必须遵循[全项目设备测试规则](device-test-rules.md)：依赖前台的测试逐方法
通过 `am start -W` 唤起并确认 `RESUMED`，每轮测试核对 `/data/misc/godmode/` 持久化日志。
